# Copy, writing quality

When a task changes user-visible text in existing interface, prose in material audit, critique, proposal, report. Checks: `practice`, `heuristic`. If project policy sets a stricter copy standard, use that.

## Authority, scope

- Read-only: quote the exact weak text. Name the pattern. Explain its effect. Propose a short fix. Keep product files unchanged.
- Implementation: edit only the copy covered by request. Check it in real state.
- Preserve approved brand, legal, compliance, support, route, analytics, search, accessibility text. If the request does not grant authority, escalate a needed change.
- Name observable writing patterns. Never guess AI authorship. Never use an AI-authorship score as evidence.

## Edit from job, voice

1. Before isolated strings, read the full copy set for surface, state.
2. Identify audience, user task, needed action, result. Voice signals (3–5): vocabulary, pace, bluntness, humor, uncertainty, formality.
3. Minimum useful edit. Preserve meaning, product terms, strong lines, useful structure, distinct voice. If you reorder a report, interface flow, record why.
4. If clearer, put the point first. Keep setup that adds needed context, trust, character. Vary structure with content.
5. Concrete nouns, direct verbs, active voice, stable terms, exact facts. Repeat the correct product term; do not rotate synonyms. Split tangled sentences. Keep useful pace changes, fragments. If product voice allows, address the reader as `you` — not “the user.” Omit unneeded gender. People-first disability language. Plain wording over culture-bound idioms.
6. Every claim stays within evidence. Name the source for metrics, quotes, awards, customer proof, research. Remove, flag, label unsupported, synthetic material.
7. Preserve variables, ICU tokens, markup, keyboard hints, accessible names, translation keys. Visible labels stay aligned with accessible names.

Done: copy states the task, state, consequence, next action in product's voice. Facts, contracts unchanged.

## Repair named patterns

| Signal | Required move |
|---|---|
| Binary contrast, negative list | State the positive claim. |
| Throat-clearing opener | Start with useful fact, action. |
| Faux-insight, lone-expert setup | Remove the setup; support the claim with evidence. |
| Rhetorical question with its own answer | Write the answer as statement. |
| Dramatic colon reveal | Normal sentence. Colons for labels, lists, quoted material. |
| Trailing clause that claims vague meaning | Name the real cause, effect, user result. |
| Importance claim with no proof | State the concrete event, change. Let evidence carry importance. |
| Vague source such as unnamed experts, studies | Cite the source, remove the claim, mark it for follow-up. |
| Inflated verb phrase | Use `is`, `has`, `can`, the exact action when shorter. |
| Synonym cycling | Repeat the stable product term. |
| Stacked fragments, repeated sentence shape | Complete, clear sentences. Vary pace only when it helps meaning. |
| Final slogan, broad metaphor, recap | End with last concrete result, risk, decision, next action. |
| Decorative format | Headings, lists, bold, emoji, dashes only when structure, product voice needs them. |
| Dash clusters | Commas, periods, parentheses. Keep a dash when it makes the sentence clearer. |
| Empty modifier, filler phrase, broad jargon | Cut it when meaning stays. Keep a domain term when users need it. |

Common filler: `utilize`, `facilitate`, `robust`, `transformative`, `crucially`, `at its core`, `it is worth noting`. Review each use in context. A word list does not establish product meaning.

## Write state copy

| State | Copy requirement |
|---|---|
| Control, navigation | Immediate action, destination; same term everywhere. |
| Loading, pending | Name known work under way. Do not invent progress, duration, certainty. |
| Empty | Distinguish first use, cleared content, unavailable data, missing setup. Offer the relevant next action. |
| No results | Name the active filter, query. Clear reset, edit path. |
| Permission | Name missing access, affected action, request/recovery path. Purpose string: one active sentence — what is collected, why. Reject “for a better experience.” |
| Error | Failed scope, retained work, safe retry, support/reference path when available. |
| Success | Confirm completed action, object once. Next useful action only when needed. |
| Destructive choice | Object, consequence, reversibility, clear cancel path. |

Keep status text compatible with live-region behavior. Avoid repeated announcements, fake reassurance, blame, dead-end messages.

## Write reports, critiques

- Lead with result, highest-severity finding.
- Tie each finding to source location, rendered state, user harm, cause, exact move.
- Separate observed facts, inference, rules, taste. Plain severity labels.
- Keep process detail only when it helps reproduce evidence, explains a limit.
- End with unresolved risk, decision, next action. Remove a recap that only repeats prior sections.
- Preserve the user's tone request. Critique interface choices, their effect on users.

## Final read

- [ ] Meaning, facts, product terms, voice stayed intact.
- [ ] Every added claim has a source, a clear synthetic label.
- [ ] Named writing patterns were removed, kept for recorded product reason.
- [ ] Variables, markup, translation keys, legal text, accessible-name contracts stayed intact.
- [ ] Loading, empty, no-result, permission, error, success, recovery copy covers each state in scope.
- [ ] Rendered copy fits narrow, wide layouts, zoom, long content, relevant locales.
- [ ] A screen-reader, accessibility-tree check verifies changed names, status messages when applicable.
- [ ] Before/after proof uses the same route, state, data, locale, theme, viewport.
